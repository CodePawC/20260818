# 草料二维码单向报修协同与院内医工闭环架构实施方案

基于草料二维码官方开放平台（cli.im/open-api）的数据协议特性与医院网络安全等保红线，将草料定位为“临床轻量扫码报修前端”，院内系统作为“医工闭环调度与资产中枢”，实现免建微信端、免外网映射的高效落地。

### User Review & Critical Decisions

> [!IMPORTANT]
> **官方技术红线核验结论（基于 cli.im/open-api 官方文档）**：
> 1. **草料官方 RDS 数据库为纯只读从库**：仅开放 `SELECT` 权限，外部系统**无法直接通过数据库写入、修改或删除**任何草料数据。
> 2. **草料开放数据服务只支持单向推送**：官方文档明确声明*“数据API服务只支持单向推送，暂不支持将外部数据写入草料”*。表单记录（报修单、巡检单）无法由外部系统通过 API 反向回写或伪造提交。
> 3. **OpenAPI 允许写入的范围仅限“活码元数据”**：通过批量活码 API 可创建或更新子码的固定属性（如设备名称、出厂编号），但无法向表单动态流插入记录。
> 
> **用户策略确认**：“让草料二维码只负责报修，院内系统做管理闭环”是完全正确且兼具成本与安全优势的最佳方案。

- **分工策略**：草料二维码负责前端扫码、临床医护手机端表单提交（支持照片/视频上传）；院内系统通过安全只读通道自动抽取报修数据，并在内网完成接单、派工、转厂修、配件消耗、验收结算全生命周期闭环。
- **网络拓扑**：院内系统单向出站拉取，无需向公网开放任何内网端口，免除微信小程序认证、SSL 证书维护与公网等保审查麻烦。

### 1. Overview & Core Concept

- **What It Does**：
  打造“临床扫码零门槛，医工闭环全可控”的轻量化协同体系。临床医护继续使用设备机身上的草料二维码微信直报故障，系统后台通过单向增量抽取引擎将报修记录秒级同步至医院设备技术台账，一键触发调度派工、外修比价与配件领用，维修结果记录于院内技术档案。
- **Target Audience / Persona**：
  1. **临床医护人员**：无需安装院内 App 或关注复杂公众号，微信直接扫机身码 30 秒快速提交报修。
  2. **医学工程科调度员 & 工程师**：在院内大屏与工作台集中处理所有草料报修，无缝流转至派工调度大厅。
  3. **科室主管与分管院长**：掌握设备故障率、响应时效、真实维修支出与三甲评审质控指标。
- **Key Value**：
  零公网暴露风险、零微信端开发成本、100% 继承全院已有 1600+ 枚草料设备活码资产。

### 2. User Experience & Visual Design

- **Key User Flows**：
  1. **临床端报修（草料前端）**：医护人员扫码 -> 填写故障现象、拍摄声画证据 -> 提交表单（留在草料云端）。
  2. **中枢自动捕获与识别（院内后台）**：院内同步引擎检测到 `table_d233` 新增记录 -> 基于 `code_id` / 出厂序列号自动匹配全院在册资产 -> 生成院内待分派工单。
  3. **医工大厅调度流转（医工中心）**：调度员一键分配责任工程师或转外修谈判 -> 工程师在内网完成修复、备件核销与验收 -> 设备状态恢复“正常运行”。
  4. **草料集成运维看板（系统配置中心）**：可视化展现数据流向拓扑（草料只读 RDS -> 院内本地库）、同步状态心跳、未处理单据统计以及 OpenAPI 凭据检测。
- **Visual Identity & Theme**：
  - 延续医工专业科技蓝（`#0284c7`）与薄荷绿（`#059669`）主基调，搭配深灰Slate工业级底色。
  - 严守 Zero-Pill 与抗 AI Slop 规范，所有草料元数据、同步频次、响应时延采用无边框文本与排版点号间隔呈现。
- **Interactive Feedback & Motion**：
  - “立即从草料拉取最新报修”按钮点击后提供微交互时延反馈与新增记录数量 Toast 提醒；
  - 扫码直查模态框支持输入或直接识别草料 URL / Code ID，高亮匹配结果与关联履历。

### 3. Key Product Decisions & Trade-Offs

- **Decision 1: 坚持单向抽取（Pull），放弃双向回写**
  - *Chosen Approach*：院内系统仅从草料只读从库拉取报修数据，不在草料端强求回写工单进展。
  - *Why*：草料官方底层不支持回写业务表单；且维修过程涉及商业机密、备件成本、原厂底价，存留在院内私有库符合医院数据合规要求。
  - *Alternatives Considered*：通过无头浏览器模拟登录草料后台回写（不稳定、极易因草料页面改版崩溃，严重违反技术规范，坚决否定）。
- **Decision 2: 混合同步机制（后台定时巡检 + 医工大厅按需一键刷新）**
  - *Chosen Approach*：默认每 15/30 分钟后台静默拉取一次；同时在医工大厅和草料看板提供“立即同步”快捷按钮。
  - *Why*：既保证了常规故障不漏单，又满足了急诊、手术室等突发故障现场报修后医工前台立等秒出的实战需求。
- **Decision 3: 保留 OpenAPI 批量活码生成拓展槽**
  - *Chosen Approach*：系统保留根据 cli.im/open-api 的“批量活码 API”创建新设备草料码的能力，但与报修业务彻底解耦。
  - *Why*：方便后续新购入设备时一键生码，而不影响现有的核心报修同步链路。

### 4. Technical Architecture & Data Strategy

```
┌────────────────────────────────────────────────────────┐
│               临床科室现场 (移动端/微信生态)               │
│  [设备草料二维码] ──> 微信扫一扫 ──> 草料极简报修表单 (拍照/录像)  │
└──────────────────────────┬─────────────────────────────┘
                           │ 提交至草料 SaaS
                           ▼
┌────────────────────────────────────────────────────────┐
│            草料二维码官方云 (cli.im / 阿里云 RDS)            │
│  • base_codeinfo (1600+ 活码资产)                       │
│  • table_d233    (报修表单真实数据)                      │
│  • 权限状态: 官方单向只读 (SELECT Only, 禁写从库)         │
└──────────────────────────┬─────────────────────────────┘
                           │ 院内系统单向出站拉取 (无公网端口暴露)
                           ▼
┌────────────────────────────────────────────────────────┐
│           五莲县人民医院 医工全生命周期智能中枢 (内网)          │
│  ┌──────────────────────────────────────────────────┐  │
│  │ 1. 增量抽取引擎 (Sync Engine)                     │  │
│  │    • 定时轮询 / 一键秒级增量捕获 (table_d233)       │  │
│  │    • code_id / SN / 院内编号多重精准对账          │  │
│  ├──────────────────────────────────────────────────┤  │
│  │ 2. 闭环调度大厅 (Dispatch & Repair Loop)          │  │
│  │    • 自动转建医院工单 (REP-CL-XXXX)               │  │
│  │    • 派工责任工程师 / 转外修返厂会商             │  │

│  ├──────────────────────────────────────────────────┤  │
│  │ 3. 草料集成运维管理面板 (Caoliao Ops Hub)         │  │
│  │    • 架构边界说明与官方 API 指南联动               │  │
│  │    • 连接心跳、同步日志、未派工待办红点提示        │  │
│  └──────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────┘
```

- **Data Model Mapping**：
  - `table_d233.code_id` ➔ `equipment.codeId`（强精准对齐）
  - `table_d233.record_id` / `记录编号` ➔ `repairRecord.id`（格式化为 `REP-CL-xxxx`）
  - `table_d233.故障表现_2645349` ➔ `repairRecord.faultDescription`
  - `table_d233.图片_2645350` / `视频_2645351` ➔ `repairRecord.photoUrl` / `videoUrl`
- **Safety & Compliance**：
  - 院内系统无任何对外端口监听，数据流纯单向进入；
  - 杜绝写入操作引发的草料数据污染风险。
